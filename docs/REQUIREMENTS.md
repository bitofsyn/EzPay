# EzPay 기능 요구사항

이 문서는 포트폴리오 설명과 실제 구현의 기준을 일치시키기 위한 핵심 요구사항과 완료 조건을 정의한다.

## 1. 인증과 권한

- 회원가입, 로그인, 이메일 찾기, OAuth 로그인, 비밀번호 재설정만 비인증 접근을 허용한다.
- 사용자 정보 수정·탈퇴·로그인 이력은 인증된 본인만 접근한다.
- 관리자 API는 `ADMIN` 역할만 접근한다.
- 사용자별 계좌·거래·통계는 JWT 사용자를 기준으로 소유권을 검증한다.

## 2. 계좌와 송금

- 사용자는 본인 계좌를 생성·조회하고 대표 계좌를 지정할 수 있다.
- 잔액은 송금·입금 같은 도메인 연산으로만 변경한다.
- 송금 계좌와 수취 계좌는 계좌 ID 오름차순으로 비관적 락을 획득한다.
- 잔액 부족, 건당 한도, 일일 한도, 동일 계좌 송금을 거부한다.
- 동일 `requestId`의 재처리는 같은 거래 결과를 반환한다.

## 3. 위험 거래와 운영 안정성

- FDS 결과는 정상, 차단, 보류로 구분한다.
- Kafka 처리 실패는 제한된 재시도 후 DLT로 이동한다.
- 알림이나 부가 데이터 저장 실패가 완료된 송금 원장을 되돌리지 않아야 한다.
- 시스템 로그와 장애 로그로 처리 실패 원인을 추적할 수 있어야 한다.

## 4. 조회와 실시간 기능

- 사용자는 본인의 거래내역, 월별 통계, 알림을 조회한다.
- 관리자는 거래량, 위험 거래, 시스템 로그와 장애 로그를 조회한다.
- SSE 연결 종료·타임아웃 시 서버의 emitter를 제거한다.

## 5. 완료 기준

- `./gradlew clean test`가 성공해야 한다.
- `npm run lint`와 `npm run build`가 성공해야 한다.
- 송금 동시성, 멱등성, 인증·인가, 한도, FDS, Kafka DLT에 대한 자동 테스트가 있어야 한다.
- README의 버전, 실행 명령, 배포 상태가 실제 구성과 일치해야 한다.

## 자동 검증 현황

- 실제 데이터베이스와 다중 스레드를 이용한 비관적 락 잔액 정합성 테스트 완료
- 본인 외 사용자 접근 차단과 JWT 사용자 기준 통계 조회 테스트 완료
- Embedded Kafka에서 잘못된 송금 메시지의 DLT 이동 테스트 완료
- DLT 메시지 DB 저장과 저장 실패 시 예외 전파 테스트 완료
- 관리자 실패 이벤트 조회·수동 재처리 API와 성공·실패 상태 기록 완료
- 관리자 실패 이벤트 조회·재처리 화면 완료
- 공개·사용자·관리자 경로의 Spring Security 필터 체인 테스트 완료
- FDS 정상·검토·차단·장애 보류 판정 테스트 완료
- 건당·일일 송금 한도 경계값 테스트 완료
- Playwright 기반 로그인·계좌 조회·송금 요청 브라우저 E2E 테스트 완료

## 현재 보강이 필요한 검증

- 전체 사용자 API의 소유권 시나리오 확대
- 실제 백엔드·데이터베이스를 연결한 사용자 송금 E2E 테스트
