# 송금 처리량 개선

송금은 API가 요청을 Kafka에 넣고 202를 돌려준 뒤, 컨슈머가 계좌를 잠그고 위험도 확인·원장 기록·알림을 처리하는 비동기 구조입니다.
2026-07 운영 DB(RDS) 부하테스트에서 처리량 천장이 약 5 TPS로 나와, 원인을 찾아 고치고 같은 조건에서 전/후를 다시 측정했습니다.

## 결과 요약

| 시나리오 | 조건 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|---|
| 로컬 DB | 지연 없음, 600건/초로 30초 제출 (18,000건) | **151 TPS**, 제출 종료 후 적체 해소 89.7초 | **541 TPS**, 4.2초 | **3.6배** |
| DB 지연 5ms | DB 왕복마다 +5ms, 100건/초로 20초 (2,000건) | **6.1 TPS**, 적체 해소 310초 | **33.7 TPS**, 39.8초 | **5.5배** |
| 메일 알림 ON | SMTP 왕복마다 +100ms, 20건/초로 10초 (200건) | **1.0 TPS**, 적체 해소 202초 | **20.1 TPS**(제출률 그대로), 0.3초 | **20배 이상** |
| 지속 고동시성 | 동시 사용자 200명이 60초간 쉬지 않고 제출 | 처리 **91.7 TPS**, 15분 안에 215,547건 중 82,562건만 처리 | 처리 **281.5 TPS**, 177,917건 전량 처리 | **3.1배** |

- 모든 실행에서 처리된 건은 전부 `SUCCESS`, 전체 잔액 합 보존, 음수 잔액 0건이었습니다.
- "DB 지연 5ms" 조건의 개선 전 수치(6.1 TPS)는 운영 RDS에서 측정한 약 5 TPS와 거의 같아, 운영 병목을 로컬에서 재현한 조건으로 봅니다.
- 개선 후 "메일 알림 ON"은 제출률(20건/초)을 그대로 따라가 천장에 닿지 않았습니다. 메일 발송은 별도 풀에서 뒤따라 처리됩니다.

## 원인과 개선

| 원인 | 영향 | 개선 |
|---|---|---|
| `transfer-events` 파티션 1개, 컨슈머 스레드 1개 | 모든 송금이 한 스레드에서 순차 처리. 건당 DB 왕복(5ms 지연 시 164ms/건으로 보아 약 30회)이 곧 처리 시간이라 DB 지연이 처리량을 그대로 깎음 | 파티션 6개 + 컨슈머 동시성 6 (`ezpay.kafka.transfer.partitions`, `ezpay.kafka.transfer.concurrency`) |
| 계좌 락을 잡은 채 SMTP 메일을 동기 발송 | 메일 1통(수백 ms~수 초)이 끝날 때까지 컨슈머와 두 계좌가 모두 묶임. 가입 시 이메일 알림이 기본 ON이라 운영에서 대부분의 송금이 이 경로를 탐 | 발송 이력(PENDING)만 남기고 커밋 후 전용 스레드 풀에서 발송. 유실되면 기존 재시도 스케줄러가 이어받음 |
| 트랜잭셔널 프로듀서 | 메시지 1건에 Kafka 트랜잭션 왕복이 더해지고, 동시 요청 수만큼 프로듀서가 생성됨. 운영에서 지속 고동시성 시 브로커 타임아웃으로 붕괴 | 멱등 프로듀서(`acks=all`, `enable.idempotence`)로 교체하고 브로커 확인 후 202 응답. 중복은 `requestId` 유니크 제약이 막음 |
| 컨슈머 `auto.offset.reset=latest`(기본값) | 새 컨슈머 그룹이 파티션을 배정받기 전에 들어온 송금을 건너뜀. 측정 중 첫 2건 유실을 확인 | `earliest`로 변경 |

병렬 처리 후에도 정합성은 기존 장치로 지킵니다.

- **계좌 비관적 락**: 항상 작은 계좌 ID부터 잠가 데드락을 막습니다.
- **`requestId` 멱등 처리**: 같은 요청이 다시 들어와도 한 번만 기록됩니다.
- **출금 계좌 기준 메시지 키**: 같은 계좌의 송금은 같은 파티션에서 요청 순서대로 처리됩니다.

## 측정 방법

[loadtest/](../loadtest/README.md)의 스크립트로 재현할 수 있습니다.

- **환경**: Apple M4 Pro 노트북 1대에서 k6, 백엔드(JVM 힙 1GB), 인프라를 함께 실행했습니다. 인프라는 Postgres 16, Kafka 7.5 단일 브로커, toxiproxy, mailpit입니다.
- **데이터**: 드라이버 유저 1명과 계좌 2,000개를 만들고, 무작위 계좌 쌍 사이에서 1,000원씩 송금합니다.
- **지연 주입**: DB와 SMTP는 toxiproxy를 거치게 하고, 응답 방향에 지연을 걸어 왕복마다 N ms가 더해지게 했습니다.
- **처리량 산정**: 제출이 끝난 뒤 DB를 폴링해 모든 건이 최종 상태가 될 때까지 기다립니다. 처리량은 처리 완료 건수를 첫 건과 마지막 건의 원장 기록 시각 간격으로 나눈 값입니다(`processing_tps`).
- **FDS 설정**: velocity 룰 임계치만 올렸고, 룰 평가 비용은 그대로 포함됩니다.
- **실행 순서**: 개선 전과 후 jar를 시나리오마다 인프라를 새로 띄운 뒤 같은 순서로 측정했습니다.

원본 결과는 `loadtest/results/*.json`에 있습니다.

## 한계와 남은 과제

- **제출 처리량 감소**: 지속 고동시성에서 제출 처리량이 3,563 → 2,930 req/s로 약 18% 줄었습니다. p50 지연은 51 → 64ms입니다. 같은 머신에서 컨슈머 스레드 6개가 HTTP 스레드와 CPU를 나눠 쓰는 영향으로 보이지만, 분리해서 검증하지는 않았습니다. 제출 실패율은 개선 전후 모두 0%입니다.
- **프로듀서 붕괴 미재현**: 로컬 단일 브로커에서는 개선 전에도 트랜잭셔널 프로듀서 붕괴가 재현되지 않았습니다. 이 항목의 개선 근거는 운영 측정 기록입니다.
- **개별 기여도 미분리**: 네 가지 개선을 함께 적용한 결과라 항목별 기여도는 따로 재지 않았습니다. 다만 DB 지연 시나리오의 5.5배는 컨슈머 6개 병렬화가, 메일 시나리오의 20배는 메일 발송 분리가 주된 요인이라고 판단합니다.
- **메일 발송 속도**: 메일은 기본 4스레드로 발송됩니다. SMTP가 느리면 메일이 송금보다 늦게 도착할 수 있습니다(`ezpay.notification.email.executor.pool-size`).
- **남은 병목**: 개선 후 다음 병목은 건당 DB 왕복 횟수입니다. 알림 피드 저장, 실시간 이벤트 발행, 위험 거래 조회를 묶거나 커밋 뒤로 미루면 더 줄일 수 있습니다.
